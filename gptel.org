** AI-DONE Apply GPTEL_PRESET to backend/model in =gptel-org--send-with-props=
CLOSED: in commit bf867c3 on branch orga
*** Origin
Reported in =~/siro-orga/siro-orga.petri.org= ("The model specified in
the GPTEL_PRESET prompt file is not obeyed").  When sending from an
org buffer that has =:GPTEL_PRESET: <name>:= in a heading's
PROPERTIES drawer, the model and backend selected via =gptel-menu=
are used instead of the ones declared by the preset.  Other settings
declared as explicit =GPTEL_*= properties on the heading already work.

*** Investigation summary
=gptel-org--send-with-props= (in =gptel-org.el=, lines ~493–510) reads
the heading properties via =gptel-org--entry-properties= and merges
them over the buffer's =gptel-backend= / =gptel-model= / etc.  When
=GPTEL_PRESET= is present it is interned and let-bound to
=gptel--preset=, but =gptel--apply-preset= is *not* called, so the
preset's =:backend= / =:model= / =:system= / =:tools= keys never
expand into the corresponding =let= bindings.  Result: the preset
name is propagated but the preset's contents are silently ignored
along the send path.

The legacy fork (=~/.emacs.d/quelpa/build/gptel/gptel-org.el=, lines
~1012–1107) handles this correctly: when an =org-preset= is found, it
calls =gptel--apply-preset= with a setter callback that captures the
preset's expansion into local =preset-*= variables, and then merges
with the priority

  : org explicit property > preset value > buffer default

via =(or org-X preset-X buffer-default)= for each setting.

*** Mission
Port the preset-expansion behaviour from the legacy fork into the
active fork's =gptel-org--send-with-props=.  Strictly limited scope:
*do not* port the legacy fork's heading-tag model lookup
(=gptel-org-model-from-user-tag= / =gptel-org-model-from-todo-tag=)
or the extra =GPTEL_INCLUDE_REASONING= / =GPTEL_REASONING_EFFORT=
properties — those are separate features and out of scope here.

Settings to honour from the preset (matching the existing set read by
=gptel-org--entry-properties=):

- =gptel--system-message=
- =gptel-backend=
- =gptel-model=
- =gptel-temperature=
- =gptel-max-tokens=
- =gptel--num-messages-to-send=
- =gptel-tools=

Priority for each: org explicit property > preset value > buffer
default (matches legacy behaviour).

*** Approach
1. In =gptel-org--send-with-props=, after destructuring the org
   properties, if =org-preset= is non-nil, call =gptel--apply-preset=
   with a setter callback that captures preset values into local
   =preset-system=, =preset-backend=, =preset-model=, etc.
2. Build the final =let= bindings using =(or org-X preset-X
   buffer-default)= for each setting.
3. Keep the existing advice registration unchanged.
4. Verify with a small test org file containing a preset that sets a
   different backend/model than the buffer default.

Reference legacy implementation: =~/.emacs.d/quelpa/build/gptel/gptel-org.el::1012=.

*** Out of scope (potential follow-ups)
- Heading-tag model overrides (=:haiku:=, =:sonnet:= etc.).
- =GPTEL_INCLUDE_REASONING= / =GPTEL_REASONING_EFFORT= properties.
- Recursion guard (=gptel-org--in-send-with-props=) — only needed if
  =gptel-request= is also advised; current code only advises
  =gptel-send= and =gptel--suffix-send=.

*** Decisions
- Non-org buffers also drop buffer-copy.  Their extractor is a
  one-shot "text above point → single user message" helper; no text-
  property tagging, no strip pipeline.  Both paths converge on the
  canonical plist schema and feed the same =gptel--format-messages=.
- Tool-call state is encoded by the heading's TODO keyword (the
  =SEQ_TODO= tool vocabulary: =BASH=, =EVAL=, =GLOB=, =GREP=, =READ=,

  wire id as its value (see the Decision sub-heading in this AI-DO).

*** Mission
Replace the =buffer-copy → strip → text-property walk= pipeline
entirely.  Two extractors feed one canonical plist schema:
- Org buffers: =org-element + TODO-state walker → canonical message

- Non-org buffers: trivial "text above point → single user message"

formatter.  No buffer-copy, no text-property tagging on either path.
All changes should live in siro-orga where possible; touch =~/gptel/=

**** AI-DONE Use TODO-state vocabulary for tool calls (no property drawers)
Each tool call gets its own heading whose TODO keyword is the tool
name drawn from the =SEQ_TODO= tool vocabulary (=BASH=, =EVAL=, =GLOB=,
=GREP=, =READ=, =WRITE=, =EDIT=, =INSERT=, =GATHER=/=GATHERING=/=GATHERED=,
=RESEARCH=/=RESEARCHING=/=RESEARCHED=, =EXECUTE=/=EXECUTING=/=EXECUTED=,
=IMPLEMENT=/=IMPLEMENTING=/=IMPLEMENTED=, =INTROSPECT=/=…ED=, etc.).
The state encodes /which tool/; the heading title encodes the call
summary.  Example:
#+begin_src org
  ,* TODO Something
  ,** AI-DO Something
  ,*** BASH Get dir content
  ,#+begin_src bash
    ls -la .
  ,#+end_src
  ls -la output …
  ,*** EVAL Checking some emacs variable
  ,*** GATHERED Something
  ,*** RESEARCHED Something
  ,**** GATHERED Something
#+end_src

Storage shape:
- Args live in a fenced =#+begin_src= block (or =#+begin_tool= if we
  keep that marker) directly under the heading.
- Result body lives either inline under the same heading (after the
  args block) or as a child heading whose state is the "-ED" variant
  (=GATHERING= → =GATHERED=, =EXECUTING= → =EXECUTED=, …).  The
  lifecycle hooks transition the state on completion.
- No =:GPTEL_TOOL_ID:= / =:GPTEL_TOOL_NAME:= property drawers.  The
  TODO keyword is the name; the heading position is the identity.

Walker behavior:
- Reads the heading's TODO state, classifies it as a tool-call /
  tool-result via the =SEQ_TODO= vocabulary, and emits
  =(:role 'tool-call :name <state-as-symbol> :args …)= and
  =(:role 'tool-result :content …)= plists.

Hook changes (=siro-gptel-hooks--pre-tool-call= /
=--post-tool-call=): instead of writing property drawers or text
properties, they create the heading with the appropriate "-ING" state
(or call-name state) on entry and transition it to the corresponding
"-ED" state when the result lands.  The result body is inserted under
the heading.

***** Decision: tool-call correlation IDs — use =org-id= with API id as value
Anthropic/Bedrock require pairing =tool_use= ↔ =tool_result= by ID.

Decision: option (c) + use the API's wire id directly as the value of
the standard org =:ID:= property.

Rationale:
- org-id accepts any non-blank, no-space string as =:ID:= value —
  =toolu_01abc=, =call_xyz= are valid; no UUID synthesis needed.
- Single source of truth: the wire id IS the org handle.  No
  translation table between an internal UUID and the API id.
- Cross-session restart works out of the box: =(org-id-find
  "toolu_01abc")= resolves directly to the heading after Emacs
  restart, via lazy load of =~/.emacs.d/.org-id-locations=.
- API providers guarantee per-conversation uniqueness of their IDs,
  satisfying org-id's non-collision requirement.
- Rejects (a): order-based pairing breaks if the user reorders or
  edits tool-call headings between requests; also fails to survive
  restart.
- Rejects (b): dropping =:ID:= after pairing causes stale entries in
  =org-id-locations=, forcing expensive full-rescans on later
  lookups; also loses audit/replay value.

Property drawer schema (one property only):
#+begin_src org
  ,*** BASH Get dir content
  :PROPERTIES:
  :ID:   toolu_01XzYabc123
  :END:
  ,#+begin_src bash
  ls -la .
  ,#+end_src
#+end_src

Lifecycle:
- ID is written at heading creation (pre-tool hook), *before* tool
  execution begins:
  : (org-entry-put nil "ID" api-id)
  : (org-id-add-location api-id (buffer-file-name))
  : (org-id-locations-save)   ; eager persist; don't wait for kill-emacs
- =:ID:= is never dropped — it stays with the heading permanently.
  The TODO state (-ING vs -ED) encodes completion; =:ID:= encodes
  wire identity.
- On restart: walker scans the conversation subtree for tool-call
  headings still in -ING state (BASH, EVAL, …) without a paired
  result; reads their =:ID:=; re-executes or marks FAILED per
  idempotency policy (TBD — separate decision).

Dependencies / preconditions:
- =org-id-track-globally= must be non-nil (default t).
- Conversation files need not be in =org-agenda-files= as long as
  =(org-id-locations-save)= is called eagerly on each ID creation
