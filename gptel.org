** AI-DONE Prefer modified visiting buffer over disk in file-based context
CLOSED: in commit 8a72b7f on branch orga
*** Origin
Reported in =siro-orga= workspace discussion: when a user adds
feedback under a TODO heading in a project doc but does *not* save
the buffer, then triggers a gptel request that has that file in
context, the AI sees the *on-disk* version — the unsaved feedback is
invisible.  Repeatedly surprises users who treat the buffer as the
source of truth.

*** Discussion highlights
Investigation traced the bug to file-based context construction:

- =gptel-context--insert-file-string= (=gptel-context.el:588=) is the
  dispatch for file context.
- Whole-file path → =gptel--insert-file-string= (=gptel-request.el:980=)
  unconditionally calls =(insert-file-contents path)= → reads disk.
- Partial-range path (=:lines= / =:bounds=) calls
  =find-buffer-visiting= *but* with predicate
  =(lambda (b) (not (buffer-modified-p b)))= — it *explicitly skips
  modified visiting buffers* and falls back to disk.  This is the
  opposite of what users expect.
- Buffer-based context (=gptel-context--insert-buffer-string=) is
  fine — it reads the live buffer via =insert-buffer-substring-no-properties=.
- =gptel-org--create-prompt-buffer= is fine — it always uses live
  buffer content for the *sending* buffer.

| Scenario                                    | What is read |
|---------------------------------------------+--------------|
| Buffer added directly                       | Live buffer ✓ |
| File added, whole file                      | Disk ✗       |
| File added with bounds, buffer unmodified   | Live buffer ✓ |
| File added with bounds, buffer modified     | Disk ✗       |

*** Mission
Make file-based context prefer a live visiting buffer over the
on-disk contents.  Concretely, in =gptel-context--insert-file-string=
(=gptel-context.el:588-608=):

1. For the *whole-file* branch, check =(find-buffer-visiting path)=
   first.  If a buffer is visiting, render its live content via
   =gptel-context--insert-buffer-string= regardless of modification
   state.  Fall back to =gptel--insert-file-string= only when no
   buffer is visiting.
2. For the *partial-range* branch, drop the
   =(not (buffer-modified-p b))= predicate from the existing
   =find-buffer-visiting= call so modified visiting buffers are
   preferred (not skipped).

Open question: should this be the unconditional default, or gated
behind a defcustom (e.g. =gptel-context-prefer-buffer= default =t=)?
Recommend unconditional + a defcustom escape hatch for users who
explicitly want disk semantics.

** AI-DONE Apply GPTEL_PRESET to backend/model in =gptel-org--send-with-props=
CLOSED: in commit bf867c3 on branch orga
*** Origin
Reported in =~/siro-orga/siro-orga.petri.org= ("The model specified in
the GPTEL_PRESET prompt file is not obeyed").  When sending from an
org buffer that has =:GPTEL_PRESET: <name>:= in a heading's
PROPERTIES drawer, the model and backend selected via =gptel-menu=
are used instead of the ones declared by the preset.  Other settings
declared as explicit =GPTEL_*= properties on the heading already work.

*** Investigation summary
=gptel-org--send-with-props= (in =gptel-org.el=, lines ~493–510) reads
the heading properties via =gptel-org--entry-properties= and merges
them over the buffer's =gptel-backend= / =gptel-model= / etc.  When

name is propagated but the preset's contents are silently ignored
along the send path.

The legacy fork (=~/.emacs.d/quelpa/build/gptel/gptel-org.el=, lines
~1012–1107) handles this correctly: when an =org-preset= is found, it
calls =gptel--apply-preset= with a setter callback that captures the
preset's expansion into local =preset-*= variables, and then merges
with the priority

  : org explicit property > preset value > buffer default

via =(or org-X preset-X buffer-default)= for each setting.

*** Mission
Port the preset-expansion behaviour from the legacy fork into the
active fork's =gptel-org--send-with-props=.  Strictly limited scope:
*do not* port the legacy fork's heading-tag model lookup
(=gptel-org-model-from-user-tag= / =gptel-org-model-from-todo-tag=)
or the extra =GPTEL_INCLUDE_REASONING= / =GPTEL_REASONING_EFFORT=
properties — those are separate features and out of scope here.

Settings to honour from the preset (matching the existing set read by
=gptel-org--entry-properties=):

- =gptel--system-message=
- =gptel-backend=
- =gptel-model=
- =gptel-temperature=
- =gptel-max-tokens=
- =gptel--num-messages-to-send=
- =gptel-tools=

Priority for each: org explicit property > preset value > buffer
default (matches legacy behaviour).

*** Approach
1. In =gptel-org--send-with-props=, after destructuring the org
   properties, if =org-preset= is non-nil, call =gptel--apply-preset=
   with a setter callback that captures preset values into local
   =preset-system=, =preset-backend=, =preset-model=, etc.
2. Build the final =let= bindings using =(or org-X preset-X
   buffer-default)= for each setting.
3. Keep the existing advice registration unchanged.
4. Verify with a small test org file containing a preset that sets a
   different backend/model than the buffer default.

Reference legacy implementation: =~/.emacs.d/quelpa/build/gptel/gptel-org.el::1012=.

**** AI-DONE Use TODO-state vocabulary for tool calls (no property drawers)
Each tool call gets its own heading whose TODO keyword is the tool
name drawn from the =SEQ_TODO= tool vocabulary (=BASH=, =EVAL=, =GLOB=,
=GREP=, =READ=, =WRITE=, =EDIT=, =INSERT=, =GATHER=/=GATHERING=/=GATHERED=,
=RESEARCH=/=RESEARCHING=/=RESEARCHED=, =EXECUTE=/=EXECUTING=/=EXECUTED=,
=IMPLEMENT=/=IMPLEMENTING=/=IMPLEMENTED=, =INTROSPECT=/=…ED=, etc.).
The state encodes /which tool/; the heading title encodes the call
summary.  Example:
#+begin_src org
  ,* TODO Something
  ,** AI-DO Something
  ,*** BASH Get dir content
  ,#+begin_src bash
    ls -la .
  ,#+end_src
  ls -la output …
  ,*** EVAL Checking some emacs variable
  ,*** GATHERED Something
  ,*** RESEARCHED Something
  ,**** GATHERED Something
#+end_src

Storage shape:
- Args live in a fenced =#+begin_src= block (or =#+begin_tool= if we
  keep that marker) directly under the heading.
- Result body lives either inline under the same heading (after the
  args block) or as a child heading whose state is the "-ED" variant
  (=GATHERING= → =GATHERED=, =EXECUTING= → =EXECUTED=, …).  The
  lifecycle hooks transition the state on completion.
- No =:GPTEL_TOOL_ID:= / =:GPTEL_TOOL_NAME:= property drawers.  The
  TODO keyword is the name; the heading position is the identity.

Walker behavior:
- Reads the heading's TODO state, classifies it as a tool-call /
  tool-result via the =SEQ_TODO= vocabulary, and emits
  =(:role 'tool-call :name <state-as-symbol> :args …)= and
  =(:role 'tool-result :content …)= plists.

Hook changes (=siro-gptel-hooks--pre-tool-call= /
=--post-tool-call=): instead of writing property drawers or text

  satisfying org-id's non-collision requirement.
- Rejects (a): order-based pairing breaks if the user reorders or

  restart.

- ID is written at heading creation (pre-tool hook), *before* tool

that, for org-mode callers, returns a /fresh narrowed indirect
buffer/ of the live source (its base if the caller itself is
indirect) instead of the upstream textual copy.  Non-org callers
fall through to =orig-fn= unchanged.  *Refinement vs. original
plan:* an indirect buffer is returned rather than =(current-buffer)=
directly — this avoids touching the =unwind-protect= in
=gptel--create-prompt= (killing an indirect buffer is benign;
killing the user's source buffer would be catastrophic).

The override is required by =siro-orga.el= and self-installs on
load via =siro-gptel-prompt-buffer-install=.

**** AI-DO Decide :ID: policy for non-tool segments (REASONED, RESPONDED)
Resolves [[*FEEDBACK Should all AI discussion responses have org-id][FEEDBACK Should all AI discussion responses have org-id]].

Background: the parser-side decision at
[[*Decision: tool-call correlation IDs — use =org-id= with API id as value]]
specifies =:ID:= on tool-call headings carrying the wire id
(=toolu_01abc= / =call_…=) for request/response correlation.  Open

Options to consider in the TODO body:

1. /Tool-calls only/ — only BASH/EVAL/GREP/… and GATHERED/EXECUTED/…
   headings carry =:ID:= (current de facto state).  Pro: minimal
   property-drawer noise; matches the "heading keyword is the
   delimiter" principle.  Con: no stable handle for re-generation or
   external references to a specific assistant turn.
2. /All AI segments/ — every AI-produced heading (REASONING/REASONED,
   RESPONDING/RESPONDED, plus tool calls) gets =:ID:=.  Pro: every
   segment is addressable by =org-id-goto=; enables future features
   like "regenerate just this turn", cross-doc references to
   reasoning, audit trails.  Con: drawer on every heading; need a
   policy for IDs of streaming segments that may be killed mid-flight.
3. /All AI segments + FEEDBACK/ — option 2 plus user FEEDBACK
   headings, making the entire AI ↔ user dialogue addressable.

Decision should specify:
- Which heading keywords get =:ID:=.
- ID source: =org-id-new= for non-tool segments vs API wire id for
  tool calls; how the two coexist (different namespace prefixes? same
  property different value spaces?).
- When the ID is written: on IB open (=-ING= state) or on IB close
  (=-ED= state)?  Open-time is safer for crash recovery; close-time
  matches "the heading is complete".
- Whether the parser-side walker uses =:ID:= for anything beyond tool
  correlation (e.g., as the =:id= key in the canonical plist for all
  segments).
